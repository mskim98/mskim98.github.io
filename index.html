트랜잭션은 INSERT 한 번으로, 요청 스레드는 커넥션 없이

판정 선행

Redis 가 재고 · 중복 발급 여부를 선제적으로 판별해 발급 가능한 요청만 통과 — DB 부하를 낮춤

STEP 2

락 대기는 트랜잭션 밖

분산락 대기 · Redis 되돌림은 트랜잭션 밖(NOT_SUPPORTED), 저장만 REQUIRES_NEW · timeout. 쿠폰 커넥션 50 → 1(락이 저장을 직렬화)

확정을 컨슈머로

요청 경로의 트랜잭션을 없애고, 재고 행 UPDATE 대신 발급 행 INSERT 한 번. 쿠폰 커넥션 1 → 4(컨슈머 병렬)

결제 승인 경로

승인은 트랜잭션 밖, 주문 확정 · Outbox 는 한 커밋 — 이벤트는 Outbox 폴러가 요청 경로와 분리해 발행

PG 승인은 되돌릴 수 없고 DB 후처리는 되돌릴 수 있다. 그래서 승인(④⑤)은 트랜잭션 밖, 주문 확정 · Outbox 적재(⑥)는 한 커밋(재고는 상품별 독립 커밋), 발행은 폴러(⑧~⑩)가 맡아 롤백된 주문의 이벤트가 나가지 않음.

결제 승인 파이프라인

트랜잭션 경계 분리와 승인 경로 서킷브레이커 — 실패가 커넥션을 붙잡지 않게

앞 장을 트랜잭션 경계로 나눈 그림 — 승인은 밖, 주문 확정 · Outbox 는 한 커밋, 승인 경로는 서킷브레이커 격리.

문제PG 승인은 되돌릴 수 없고 DB 후처리는 되돌릴 수 있는데 한 경계 안에 있어, 결제만 성립하고 주문은 미확정인 상태가 남음. PG 가 느려지면 승인 호출이 그대로 대기 — 5초 지연 주입 시 PG 에 닿은 호출 p95 5.65초
해결승인은 트랜잭션 밖(NOT_SUPPORTED), 후처리는 독립 트랜잭션(REQUIRES_NEW)으로 분리. 결제완료 이벤트는 Outbox로 주문 확정과 같은 커밋에 적재, 재고 차감은 상품별 독립 커밋(도중 실패 시 복원), 서킷브레이커를 승인 · 취소 경로에 각각 배치
결과서킷브레이커 fast-fail로 장애 격리 — 승인 경로 p95 5.65초 → 649.2ms. 5s 지연 + 500 주입 구간 호출 682건 중 667건을 PG 미도달로 차단, 실제 PG 에 닿은 것은 15건
5.65초PG 에 닿은 승인 p95서킷이 막기 전 15건 · 5초 지연 주입
649.2ms승인 fast-fail p95서킷브레이커 장애 격리
667 / 682건PG 미도달로 차단응답 1.5초 이하 = PG 미경유 (스텁이 모든 승인을 5초 지연)

PG 결제 보상 파이프라인

Toss Payments 승인 이후 DB 후처리 실패를 사람 개입 없이 보상

PG 승인 뒤 DB 후처리가 실패하면 결제만 성립하고 주문은 미확정인 구간 발생 — 보상 배치가 PG 취소까지 자동 처리.

재시도 · 백오프 · 회로 값이 서로를 참조해 정해진 근거

① 재시도 5회 · 백오프 2·4·8·16분
배치 5회가 유일한 취소 경로라 중간에 포기할 수 없다. 백오프 합 30분이 하한이고, 상한은 PG 멱등키 유효 기간 — 그보다 길면 같은 키로 재시도해도 PG 가 받지 않는다.

② OPEN 45초 vs 배치 주기 30초
OPEN 이 주기보다 15초 길게 잡혀 있어, 서킷이 열린 동안 다음 회차는 반드시 한 번 생략된다. 감수한 비용.

③ 상태 머신 · 멱등키 고정
결제 · 보상 상태는 상태 머신으로 관리하고, 재시도마다 같은 멱등키를 써 이중 승인 · 취소를 막는다.

콜백이 이벤트 루프를 막을 때

한 사용자의 콜백 블로킹이 같은 루프가 맡은 다른 사용자 스트림까지 멈춘다

이벤트 루프는 여러 커넥션을 함께 맡아, 블로킹 콜백을 그 위에서 돌리면 피해가 남의 요청까지 번진다. 콜백 블로킹을 300ms 로 키우자 다른 세션 첫 청크가 316ms 밀림 — publishOn 뒤 1~19ms(5회).

LLM 호출 · 세션 안정화 계층

장애 전파는 서킷으로 끊고, 비정상 전이는 막되 고착 상태는 회수한다

문제외부 LLM 은 느려지거나 응답하지 않는다. 끊는 것만으로는 부족하고, 끊긴 뒤 세션이 어느 상태에 멈춰 있는지까지 정해야 다음 요청이 받아들여진다. 그래서 서킷(호출)과 상태 기계(세션)를 함께 설계했다.

해결① 서킷 — 최근 호출 창의 실패율로 열고, 시험 호출로 닫는다
해결③ 서킷 범위를 구독 시점까지 넓힌다 — 반쪽 구간은 실패 주입으로 발견

chatStream 이 메서드 본문에서 히스토리 조회와 RAG 벡터 검색을 동기로 했다. Redis · 벡터 스토어가 죽으면 Flux 를 만들기도 전에 예외가 나가는데, 리액티브 서킷은 구독 시점부터 감싼다 — 그 실패는 한 건도 집계되지 않았다.

조회 · 조립을 Flux.defer 로 구독 시점까지 옮겨 검색 실패까지 서킷 안으로 편입. 실패 주입이 아니면 초록으로 남았을 결함.

같은 결함의 두 번째 증상 — 에러 콜백을 건너뛰어 세션이 PROCESSING 에 고착, 첫 요청 500 뒤 2~6번째 연속 401. 감수한 비용 — subscribe() 전에는 아무 검증도 일어나지 않음

해결② 세션 상태는 선언된 (상태, 이벤트) 쌍으로만 — 빈 응답 · LLM 일시 실패로 PROCESSING 에 고착된 세션을 회수하는 전이를 따로 둠
결과시험용 엔드포인트(/test/circuit, LLM 과 같은 서킷 설정)에 3초 지연을 심은 부하 243,820건 중 95%가 1.76ms 안에 응답(서킷의 즉시 거절) · 최댓값 3,026ms 는 서킷이 막기 전 3초를 그대로 기다린 호출
